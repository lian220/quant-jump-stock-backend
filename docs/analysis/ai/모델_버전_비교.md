## 🎯 결론부터

**ML 모델 로직과 알고리즘은 완전히 동일합니다!**

유일한 차이점은 **데이터베이스 백엔드**뿐입니다:
- GitLab: Supabase (PostgreSQL) → 테이블 구조
- Local: MongoDB → `daily_stock_data` 컬렉션
- Quantiq 현재: MongoDB → 분산 구조 (❌ 잘못됨)

**권장 방향**: Local stock-trading 구조를 따르면 검증된 ML 모델을 즉시 사용 가능

## 📊 3가지 버전 비교

### 1️⃣ GitLab Repository (banbu-stocktrading)

**데이터베이스**: ❌ **Supabase (PostgreSQL)**

**데이터 구조**:
```python
# Supabase 테이블: economic_and_stock_data
{
  "날짜": "2026-01-31",

  # 주식 가격 (27개 컬럼)
  "애플": 150.25,
  "마이크로소프트": 380.50,
  # ... 25개 더

  # 경제 지표 (37개 컬럼)
  "GDP": 123.45,
  "실업률": 3.7,
  # ... 35개 더
}
```

**특징**:
- ✅ 날짜별 단일 행(row)에 모든 데이터 통합
- ✅ 관계형 DB 구조 (컬럼 기반)
- ❌ MongoDB와 호환 안됨
- ❌ 현재 Quantiq 프로젝트와 DB 타입 자체가 다름

---

### 2️⃣ Local Repository (stock-trading)

**데이터베이스**: ✅ **MongoDB**

**데이터 구조**:
```javascript
// MongoDB 컬렉션: daily_stock_data
{
  _id: ObjectId("..."),
  date: "2026-01-31",

  // FRED 경제 지표 (중첩 객체)
  fred_indicators: {
    "Treasury_10Y": 4.2,
    "USD_KRW": 1462.89
  },

  // Yahoo Finance 지수 (중첩 객체)
  yfinance_indicators: {
    "SP500": 4500.12,
    "NASDAQ": 15000.34,
    "KOSPI": 2600.0
  },

  // 개별 주식 (중첩 객체)
  stocks: {
    "AAPL": { close_price: 150.25 },
    "MSFT": { close_price: 380.50 }
  },

  updated_at: ISODate("...")
}
```

**특징**:
- ✅ 날짜별 단일 문서에 모든 데이터 통합
- ✅ MongoDB 중첩 객체 구조
- ✅ 현재 22,002개 문서 존재 (검증됨)
- ✅ `predict.py` (30K+ 라인)가 이 구조 사용

### 3️⃣ Quantiq 현재 (❌ 잘못된 구조)

**데이터베이스**: ✅ **MongoDB** (동일)

**데이터 구조** (❌ 잘못됨):
```javascript
// fred_data 컬렉션 - 지표별, 날짜별 개별 문서
{
  date: "2026-01-23",
  code: "DEXKOUS",
  name: "USD_KRW",
  value: 1462.89
}

// yfinance_data 컬렉션 - 티커별, 날짜별 개별 문서
{
  date: "2026-01-30",
  ticker: "GC=F",
  name: "Gold",
  close: 4713.90
}
```

**문제점**:
- ❌ 데이터가 날짜별로 분산됨
- ❌ `daily_stock_data` 컬렉션 사용 안함
- ❌ Local stock-trading의 predict.py와 호환 안됨
- ❌ 날짜별 통합 조회가 비효율적

## 🔄 데이터 처리 흐름 비교

### GitLab 버전

```python

response = supabase.table("economic_and_stock_data").select("*").execute()
df = pd.DataFrame(response.data)

# 2. 정규화
scaler = MinMaxScaler()
data_scaled = scaler.fit_transform(df[all_features])

# 3. 시퀀스 생성 (90일 lookback)
for i in range(90, len(data_scaled) - 14):
    X_stock_seq = data_scaled[stock_features][i-90:i]
    X_econ_seq = data_scaled[econ_features][i-90:i]
    y = data_scaled[stock_features][i+14]  # 14일 후 예측

# 4. 모델 학습
model.fit([X_stock, X_econ], y, epochs=50, batch_size=32)

# 5. 예측 후 Supabase에 저장
supabase.table("predicted_stocks").insert(predictions).execute()
```

## 🎯 최종 결론

### ✅ 동일한 것들

1. **ML 모델 아키텍처** - Transformer, Dual-Input, 8 heads, 256 dim
2. **학습 파라미터** - 50 epochs, batch 32, lr 0.0001
3. **데이터 처리 로직** - 90일 lookback, 14일 예측, MinMaxScaler
4. **입력 데이터** - 27 주식 + 37 경제지표
5. **예측 방식** - 시계열 시퀀스 기반 예측

### ❌ 다른 것

**오직 데이터베이스 백엔드만 다름:**
- GitLab: Supabase (PostgreSQL) → 테이블 구조
- Local: MongoDB → 문서 구조
- Quantiq: MongoDB → 분산 구조 (수정 필요)

## 💡 Quantiq의 방향

**권장: Local stock-trading 구조 (MongoDB - daily_stock_data)**

**이유**:
1. ✅ 동일한 MongoDB 사용 중
2. ✅ Local predict.py (30K+ 라인)와 호환
3. ✅ 이미 22,002개 문서로 검증된 구조
4. ✅ 날짜별 통합 조회 성능 우수
5. ✅ 검증된 ML 모델 그대로 사용 가능

**GitLab 버전은 사용 불가**:
- ❌ Supabase (PostgreSQL) vs MongoDB (다른 DB)
- ❌ 완전히 다른 데이터 구조
- ❌ 마이그레이션 비용 높음
