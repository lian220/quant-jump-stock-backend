본 incident 조사 과정에서 **추천 PR #72 (`investigate/slack-vs-page-recommendations`)** 가 머지되었고 그 안에 코드 변경 hotfix가 포함되었다. 결과적으로 **회귀**가 되었다.

### 회귀 원인

진단 과정에서 Secret Manager `v20` 시점의 키 이름(`GCP_PROJECT_ID` 등)을 확인하고 **"코드 alias를 GCP_*로 통일"** 방향으로 hotfix 결정했다. 그러나 같은 시간대에 사용자가 `v21`로 secret을 **VERTEX_AI_***로 정정 중이었다. 두 변경의 시점이 교차하면서 충돌:

- Secret: `GCP_*` → `VERTEX_AI_*` (사용자가 코드에 맞춤)
- Code: `VERTEX_AI_*` → `GCP_*` (우리가 secret에 맞춤)

방향이 정반대였다. 양쪽 변경 후 또 매칭 실패.

### 학습

1. **운영 변경 중인 자원의 *현재 시점 진실*을 사람이 변경 중일 수 있음**. 진단 도중 운영자가 동시 정정을 가하는 시나리오를 가정 안 했다.
2. **Secret Manager 변경 알람이 없었음**. v21 생성을 우리가 인지할 방법 없음. 결과: 우리는 v20 기준으로 의사결정, 사용자는 v21로 정정.
3. **hotfix 머지 직전 secret 최신 상태 재확인 단계 부재**. 코드 변경이 직접 환경변수 매핑을 건드릴 때는 머지 직전 secret diff 확인이 mandatory.
4. **단일 incident 안에서 진단과 hotfix를 한 PR로 묶은 게 위험**. 진단(읽기 전용 분석) + hotfix(코드 변경)는 분리되어야 함. 진단 PR이 머지되어도 운영에 영향 없어야 안전.
